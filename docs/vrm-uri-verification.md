# URI方式の実装・検証結果

2026-11-09、ユーザー配置のVRM_NekoUmiushi.vrm（1,049,112 bytes）を使用した。
VS Code Extension Hostの検証コードで測定し、全テストが終了コード0で完了した。

## 実装

ローカルファイルの存在を確認し、WebviewごとのasWebviewUriで渡す方式に変更した。
モデルのbase64化と巨大なpostMessageを廃止し、許可ディレクトリを拡張本体と選択モデルの親に限定した。
CSPはローカル資源とモデル内のdata/blob資源を許可する。
Three.jsのImageBitmapLoaderはblob URLをfetchするため、img-srcだけでなくconnect-srcにもblobの許可が必要だった。
この許可が欠けていた段階の実機テストは描画タイムアウトになり、修正後に再検証した。

VRMとVRMAを並行ロードし、VRMAを待たずにモデルを表示する。
設定変更前のロード結果はキャンセル扱いにし、後から表示を上書きしない。
モデルの切替・破棄時にはMixerとVRMのGPU資源を解放する。
非表示時はCanvasのframeloopを停止し、復帰時のアニメーションdeltaを50msに制限する。
非表示中のモデル設定と診断件数はProviderに保持し、可視化時に最新値を送る。

## 性能

初期表示は最終版の別プロセスで3回、再表示は同じモデルで30回測定した。

| 対象            |   中央値 |     p95 |     最大 |
| --------------- | -------: | ------: | -------: |
| 初期表示（3回） | 264.23ms |       — | 288.89ms |
| 再表示（30回）  |  23.06ms | 28.80ms |  29.57ms |

初期表示の個別値は264.23ms、288.89ms、224.37msだった。
今回の最終版では初期表示3/3回、再表示30/30回が300ms以下だった。

計測範囲は初期表示がresolveWebviewView開始から描画処理後の応答まで、再表示が可視化通知から描画処理後の応答まで。
拡張の起動・パスのstat処理、入力から可視化通知まで、GPUやOSの表示完了は含まない。
任意のモデルやコールドスタートで300ms以内を保証する結果ではない。
調査途中の別版では初期表示が約6.2秒になる外れ値もあり、初期表示の速度保証にはより広い条件での測定が必要である。

前段階のbase64版の初期表示中央値は290.92ms、再表示は21.61msだった。
今回はテストプロファイルでユーザー拡張を隔離するなど測定環境も整えたため、この差をURI化単独の効果とは扱わない。
変更前後の比較はvrm-performance-comparison.mdを参照。

生データはvrm-uri-results.jsonに保存した。
初期表示3回のうち1回はfullRun、残りはadditionalInitialRunsに記録されている。
fullRunの最初の30件のresumeが通常の再表示性能測定で、それ以降は回帰検証である。

## 回帰検証

| 項目                                                     | 結果                                              |
| -------------------------------------------------------- | ------------------------------------------------- |
| 30回の検索→Explorer往復                                  | 同一documentId、モデルロード回数1回を維持         |
| 30秒の非表示                                             | 前後の描画フレーム差は1、非表示中の連続描画を停止 |
| アニメーションの復帰                                     | 更新deltaは50ms以下                               |
| 非表示中の診断更新                                       | 復帰したモデルのissuesCountに反映                 |
| サイドバーの閉じる→開く                                  | 3回成功、モデルロード回数1回を維持                |
| 非表示中のモデル変更                                     | 6回成功、描画応答のURIが指定ファイルと一致        |
| GPU資源                                                  | geometryは1、textureは3で、往復・切替後も一定     |
| 再生成後の状態同期                                       | Providerのテストで最新モデル・診断件数を確認      |
| 古いモデルのロード完了                                   | 新モデルを上書きせず、古い資源は1回だけ破棄       |
| VRMA失敗                                                 | ロード処理のテストでモデル表示を維持              |
| モデル未設定・存在しないファイル・ディレクトリ・HTTP URL | テストで除外を確認                                |

ローカル許可ディレクトリを変更する設定切替では、VS CodeがWebviewを再生成する場合があった。
この場合はモデルロード回数が新しいdocumentId内で1回へ戻るため、切替後のURIと資源数で判定した。
モデルを変更しない通常のタブ往復では再生成されなかった。

GPU資源数と描画フレーム数は、資源増加と非表示時の描画負荷を確認する指標である。
OS全体のCPU使用率やプロセス総メモリ、GPUコンテキスト喪失を強制した試験は実施していない。
動画によるフレーム単位の表示完了測定も実施していない。

## 再現

インストール済みVS Codeを指定して実行できる。
モデルはユーザーのローカルパスを渡し、モデル本体をリポジトリへ追加しない。
検証用プロファイルは一時ディレクトリに作成され、通常のユーザー設定は変更しない。
性能テストの切替試験だけは、同じモデルを一時ディレクトリへコピーして別ファイルパスを作り、終了時にそのコピーを削除する。

```sh
export VSCODE_EXECUTABLE_PATH='/Applications/Visual Studio Code.app/Contents/MacOS/Code'
export VRM_MODEL_PATH='/absolute/path/to/model.vrm'
npm run compile
npm run test:regressions
export VRM_PERFORMANCE_LOG="$(mktemp /tmp/vrm-performance.XXXXXX)"
npm run test:performance
```

初期表示だけ追加測定する場合は、空のログ出力先を指定して次を実行する。

```sh
VRM_PERFORMANCE_QUICK=1 VRM_PERFORMANCE_RETURNS=0 npm run test:performance
```

test:regressionsは5件の状態遷移・失敗ケースを検証する。
性能テストは時間そのものを固定の合否基準にせず、生データを記録する。
ハードウェアに依存しないロード回数・描画停止・状態同期・資源数はassertで検証する。
