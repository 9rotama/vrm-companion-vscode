≤ 300 msを実測

registerWebviewViewProviderの第3引数に{ webviewOptions: { retainContextWhenHidden: true } }を渡す。JSON状態保存だけでは、解析済みThree.jsオブジェクトやGPU資源は復元できないため、このモデル表示には保持を優先する。

保持にはメモリ負担がある。非表示時は描画・アニメーション更新を抑え、復帰時の巨大なdeltaも抑制する。Webviewの実破棄、ウィンドウ再読込、GPUコンテキスト喪失時は通常のロードへ戻れる設計とする。

第2段階：初回表示の待ち時間を減らす

ローカルファイルをURIで渡す

base64化と全文postMessageを、設定されたローカルVRMのasWebviewUriへ置換する。モデルの親ディレクトリを必要な範囲だけlocalResourceRootsに追加。CSP・共有メッセージ型・設定変更時のURI更新も揃える。外部モデル取得は追加しない。

モデル表示とVRMA準備を分離

VRMとVRMAを並行ロードし、VRMが用意できたら先に表示する。VRMA完了後にMixerを接続する。VRMA失敗でも静止モデルは表示する。設定変更で古いロードが後から反映されないよう世代管理と資源解放を入れる。

まず第1段階だけで計測し、再表示の300ms達成を確認する。第2段階は初回計測のボトルネックに応じて進める。

状態同期も併せて整える

現在、設定変更後のモデルが初期送信用データへ反映されない。最新のモデル設定・診断件数をProviderに保持し、再生成時と再表示時に同期する。メッセージ受信リスナーはmounted送信より先に登録し、設定イベントは該当キーの変更だけに絞る。非表示中のメッセージ配送だけに依存しない。

既存の.vscode/launch.json「Run Extension」で起動。対象マシン、VS Code版、モデルのサイズ・ポリゴン数・テクスチャ情報を記録する。ユーザーのローカルモデルを使用し、検証用モデルをリポジトリに追加しない。

  1. 変更前の基準値：初回表示とタブ往復を計測。画面録画でタブ操作からモデル表示までを確認する。
  2. デバッグ計測：表示切替に識別子を付け、Extension Host側の可視化通知からWebviewの描画完了応答までをHostの単一時計で記録。Webview側は復帰、VRM/VRMA解析完了、VRMを含む最初のrender完了を個別に記録する。
  3. 表示の裏付け：render直後のマーカーだけでは実際の画面合成完了を保証しない。画面録画と照合し、非表示区間の描画や空フレームを完了扱いにしない。画面操作から可視化通知までの遅延も録画で確認する。
  4. 反復：モデルを一度表示後、別サイドバーへ移り戻る操作を30回。短い非表示・30秒の非表示・サイドバー開閉で確認。再表示時にmountedやVRMロードが増えないことを確認する。
  5. 回帰：非表示中のモデル変更・診断更新、モデル未設定・削除、VRMA失敗、ウィンドウ再読込を確認。往復後のメモリ増加や非表示中のCPU負荷も見る。

4. 今後も使うテスト

既存のテストはサンプルのみ。大きなE2E基盤の新設は今回の前提にせず、意味のある状態遷移を検証する。

  • Providerの状態同期：モデルA→Bの変更後にWebviewが再生成されてもBが届くこと、非表示中の診断変更が復帰後に反映されること。
  • 非同期ロードの競合：Aの読込中にBへ変更し、Aが遅れて完了してもBを上書きしないこと。
  • 障害時の表示：VRMAが失敗しても読み込めたVRMが表示されること。
  • 再現可能なデバッグ手順：計測ログと手順を残す。300msの判定は、ハードウェア依存のため通常のユニットテストへ固定しない。
